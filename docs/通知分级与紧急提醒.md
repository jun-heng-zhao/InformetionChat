# 通知分级与紧急提醒

文档版本：1.3-draft。不同聊天和信息插件统一向宿主提交通知，宿主决定展示、排序、声音和弹窗。适用于中心化或去中心化来源，不绑定某个服务运营方。

## 0. M1 简单目标

首版以“用户为测试插件开启紧急来源 → 插件发布有效事件 → 宿主前台弹窗 → 用户关闭或插件撤回”为完整流程。四级枚举保留，重点验证 `critical`；不以后台常驻、操作系统关键提醒、真实地震源或推送中继为前提。

M1 实现 publish、update、withdraw、get/list 和 policy.get；确认动作由宿主弹窗处理，插件/Agent 代确认与 Agent 主动发布通知后续按需开放。来源使用宿主分配的本地安装来源 ID，无需外部账号或中心注册。

应用处于后台时记录 `received` 并返回 `FOREGROUND_REQUIRED`；回到前台后重新检查授权、有效期和事件状态，再决定展示。不能把未展示的记录写成 displayed。第 6 节的系统通知属于后续适配目标。

## 1. 四级提醒

| 等级 | 典型用途 | 应用前台（M1） | 后台/锁屏（后续） |
|---|---|---|---|
| `passive` 静默 | 同步完成、一般订阅更新 | 通知中心或角标，不打断 | 默认不弹出、不发声 |
| `normal` 普通 | 普通聊天消息 | 角标、列表或轻量横幅 | 按会话设置使用系统通知 |
| `important` 重要 | 用户关注的联系人、提及、限时任务 | 醒目横幅，可按设置发声 | 高重要性通知，仍遵守系统设置 |
| `critical` 紧急 | 用户启用的地震预警等紧急来源 | 已授权时直接显示宿主紧急弹窗，可附声音/震动 | 请求系统允许的最高适用提醒方式；权限不足明确降级 |

等级表示打断需求，不证明消息内容或来源真实性。宿主显示插件、连接账号/来源和通知时间，不允许插件冒充其他来源。紧急弹窗由宿主绘制，避免多个插件独立创建覆盖窗口。

默认最高等级为普通。用户可按插件、连接来源、会话或类别调整上限、声音和打断方式；紧急弹窗由用户事先为具体来源开启，此后该范围内的有效提醒可以直接弹出，无需每次再次授权。

## 2. 请求等级与实际等级

插件声明通知类别及请求的最高等级，发送时提供 `requestedLevel`。宿主根据已授权能力、该来源的用户策略、免打扰设置、当前平台能力和消息有效期计算实际等级与展示方式。消息正文写“紧急”不能提升权限。

紧急弹窗同时要求 `notification.publish`、`notification.critical`、已登记类别和该来源的紧急提醒授权。未授权的请求按允许的等级展示，并返回降级原因；插件无法通过更换标题或类别绕过上限。未知类别直接拒绝，不能动态创建已获授权的紧急来源。

用户可以另行允许指定紧急来源突破应用内部免打扰；突破操作系统免打扰取决于系统许可。提高等级上限、改变来源和增加类别的敏感权限都需要用户授权。随包模块与其他插件使用同一规则。

## 3. 宿主接口

| 方法 | 行为 |
|---|---|
| `host.notification.publish` | 提交通知请求，返回宿主通知 ID、实际等级、展示状态及降级原因 |
| `host.notification.update` | 对同一来源事件发布更高修订，更新内容、到期时间或等级 |
| `host.notification.withdraw` | 撤回本插件的有效通知，保留必要的状态记录 |
| `host.notification.list/get` | 读取当前调用方有权查看的提醒状态与来源 |
| `host.notification.acknowledge` | 用户确认已看到；普通程序或 Agent 不默认拥有代确认权限 |
| `host.notification.policy.get` | 返回当前授权等级、系统能力、免打扰及展示限制 |

这些接口是宿主公共能力，聊天、预警、日历等插件均可复用，无需各自实现弹窗系统。后续事件/Agent 适配器也通过同一权限代理调用，M1 不依赖通用事件总线。通知 policy 的提升只通过可信宿主界面或明确授予的设置管理操作，插件不能自行改上限。

## 4. 数据契约

最低字段：类别、`sourceId`、`eventId`、修订号、请求等级、标题、正文或受控引用、`occurredAt`。紧急提醒必须提供 `expiresAt`，区分事件产生时间与宿主接收时间。

```json
{
  "category": "local-test-alert",
  "sourceId": "installation-source-17",
  "eventId": "source-event-20260918-001",
  "revision": 1,
  "requestedLevel": "critical",
  "title": "紧急提醒测试",
  "body": "这是一条用户主动触发的本地测试提醒。",
  "occurredAt": "2026-09-18T02:00:00Z",
  "expiresAt": "2026-09-18T02:01:00Z",
  "actions": [{"id":"open-details", "label":"查看详情", "command":"alerts.open-details"}]
}
```

这是静态接口样例，实际测试使用当前时间和 60 秒有效期；按样例日期回放时必须判定过期。通知类别和 actions 命令须先由测试插件声明，不能把此段 JSON 当作可直接激活的插件包。来源标签和插件身份由宿主安装记录/连接绑定生成，不信任正文自报。Agent 发出的提醒绑定其会话来源，不能冒充聊天或预警插件。动作只能调用该插件已声明的命令，再次按用户授权执行，不能直接注入脚本或任意链接。

去重键为工作区、安装、来源和 eventId；同键更高修订才更新状态，同修订且相同内容返回现有结果，同修订不同内容拒绝，较低修订不能覆盖新状态。withdraw 也需更高修订，宿主保存终止记录直至事件原有效期结束，防止重放复活。M1 已确认或撤回的 eventId 不再次弹窗；确有新事件须使用新 eventId。不同来源相同正文不自动合并。修订提升等级是否再次弹出，由授权策略和事件状态决定。

已过期的紧急事件不能在重连、重启或缓存回放时作为新预警弹出，只能进入历史并标明过期。M1 初始限制：标题 120 字符、正文 2,000 字符、最多 2 个动作；未来偏差不超过 30 秒、有效期不超过 5 分钟、每来源每分钟最多 3 个新的紧急弹窗。超限返回 `RATE_LIMITED` 并显示限流状态，阈值为待验证配置。系统时间明显回退时暂停缓存事件重弹，直到重新校验；重放和洪泛合并为可见状态，不得静默丢弃后又谎报已展示。

## 5. 弹窗、隐私和并发

前台紧急弹窗置于宿主当前工作区上层，显示来源、时间、正文摘要和关闭/查看操作。用户可明确关闭，不因插件循环上报同事件而无限重新弹出。多个紧急事件按等级、时效和到达顺序协调，保留事件列表，避免插件相互覆盖。

锁屏正文默认按用户隐私设置隐藏。只有声明对应数据范围并获授权的插件或 Agent 才能读取通知详情；跨插件聚合不扩大对原始聊天的权限。

区分 received、displayed、acknowledged、expired、withdrawn 等状态。系统接受通知提交不等于用户已经看到；“我知道了”仅表示本地确认，不自动产生聊天已读回执或向来源外发信息。外发回执应作为独立受授权操作。

## 6. 后续平台适配与限度

- 桌面：应用前台使用宿主弹窗；后台使用系统通知及用户允许的应用窗口提示，不能假定系统总允许抢占焦点。
- Android：使用通知渠道与用户设定的重要性；声音、震动、悬浮提示及锁屏展示受系统设置约束。全屏通知受系统版本、用途和分发规则限制，不作为任意插件的默认能力。
- iOS：使用系统通知与适用的高时效能力；关键提醒需要应用具有相应 entitlement 且用户授权。插件自身不能授予这些权限。
- 断网、应用未运行、后台被系统限制或来源没有送达时，宿主无法保证及时提醒。宿主必须显示连接和通知权限状态，不能把这个客户端宣称为保证送达的预警系统。

界面在用户启用紧急来源时显示当前可用方式。M1 为“仅应用前台弹窗”；系统通知完成适配后才显示后台方式。可以提供用户触发的测试提醒，但测试不代表未来后台必然送达。

## 7. 验收（先验证 M1 前台范围）

- 用户授权的有效紧急来源在前台直接弹窗；普通聊天不能通过自报 critical 获得同样权限。
- 每插件/来源/类别策略独立，多聊天插件使用同一提醒中心且保持来源可辨认。
- 重复、乱序、撤回和过期事件不产生错误的新预警；消息更新可追踪。
- M1 应用内免打扰和后台无法展示时，状态与降级原因可查询；系统通知关闭及关键提醒权限不足在后续适配时验证。
- 停用来源撤销待处理通知，历史保持可查；已经展示的结果按宿主状态更新。
- 后续开放 Agent 通知方法时，只能在授权范围查询、产生提醒或请求展示；没有额外授权时不能提高等级、修改通知策略或替用户确认紧急信息。

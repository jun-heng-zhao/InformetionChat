# 设计审查与修改记录

日期：2026-09-18。审查对象为当前 README、docs 下的设计/契约/ADR/治理文档，并只读对照格式转换原型与历史设计。背景：个人开发者、无官方团队或基础服务；重点为插件功能，Agent 与紧急通知采用简单目标。本次止于设计、文档修改与静态检查。

## 1. 审查结论

插件宿主方向成立，主要不足是首版范围混合、跨端隔离缺少验证门槛、接口只有方法清单、简单 Agent/通知被复杂平台能力牵连，以及历史团队业务残留。修订后以一个桌面平台的插件加载、隔离、服务互通和复用为核心，同时验收 Agent 调用服务与授权紧急通知前台弹窗。

文档已形成统一设计基线，仍属于草案。没有生产宿主或正式 SDK，不能把清单验证、示例页面、目标平台和本文修订当成实现通过。完整文档及状态见[开发文档索引](开发文档索引.md)。

## 3. 首版完整验收主线

1. 在 Linux Electron 客户端断网加载两个本地插件；来源、摘要、代码执行风险、插件/工作区信任、权限、服务描述和错误原因可查看。
2. 查看器通过宿主 API 只能传递用户选定的输入；转换器通过服务入口生成结果，宿主保存输出，双方宿主管理的私有存储不可互访。已信任 Node.js 进程的系统访问不在该权限保证内。
3. 存在多个提供者时由用户绑定；缺少、停用、升级不兼容、循环依赖和调用超时均有明确结果。
4. Agent API runtime 使用独立 home/workspace/profile/session 运行；模型只看到插件选择暴露且当前获授权的工具，调用同一服务并返回结构化 run 结果，不点击插件页面或自行扩大授权。
5. 用户开启测试插件的紧急来源，前台有效事件直接弹窗；未授权降级，重复不重弹，过期及撤回事件不复活。
6. 停用、取消、权限撤销及更新失败分别验证：旧通道/句柄失效，失控运行时可回收，包与数据恢复一致。

WASM/OS 沙箱、轻量移动信息收发器、联网协议、后台推送、完整备份和 Agent 高副作用工具按后续阶段验收，不应把这些能力默认添加到首版依赖。

## 7. 首次实现（M1 演示）复核：2026-09-18

本节记录首次把契约落成可运行代码后的复核结果。演示范围与运行方式见[开发环境与运行说明](开发环境与运行说明.md)；本节只记录发现与结论，不重复操作步骤。

### 7.1 M0 平台选型与后续决策（对应 R02）

R02 最初要求确认 Flutter 桌面的 WebView 绑定。候选检查结论：

| 方案 | 最新版本 | 支持平台 | 结论 |
|---|---|---|---|
| `webview_flutter` | 4.14.1 | android / ios / macos | **官方不支持 Linux 桌面**，与"Linux 先验证"的假设冲突 |
| `webview_cef` | 0.6.2 | linux / windows / macos | 基于 CEF，但公开 API 缺少所需逐请求拦截和逐安装上下文；补齐需维护原生 fork |
| `desktop_webview_window` | 0.3.0 | linux / windows / macos | 基于 WebKitGTK，但为独立窗口而非内嵌控件 |
| `access-company/flutter_linux_webview` | 0.1.3（2024-08 停更） | linux | 依赖 `webview_flutter_platform_interface ^1.8.0`，锁死 `webview_flutter` 3.0.4，无法与 v4 共存 |
| `flutter_inappwebview` | 6.1.5 | 不含 linux | 不适用 |
| Electron | 版本待桌面工程锁定 | linux / windows / macos | 随应用分发 Chromium，支持同源 iframe、MessageChannel、请求拦截和 Node Extension Host；采用 VS Code 式插件信任 |

表中的平台是候选组件的上游支持信息，不代表项目目标。项目开发顺序已经冻结为 Linux、Windows、Android、iOS，不规划 macOS。

结论：Flutter 路线缺少满足要求的 Linux 官方 WebView。后续已通过 [ADR 0009](adr/0009-electron-desktop-plugin-runtime.md)选择 Electron，不再继续 Flutter WebView 选型。R02 的技术决策已关闭；Electron/Chromium 版本、iframe 边界、信任流程、资源消耗和回收仍需 M0 实测。

### 7.2 实现中发现并修正的设计偏差

| 编号 | 优先级 | 问题 | 处置 |
|---|---|---|---|
| R13 | P1 | 契约写"结果句柄绑定调用方会话 / 输出重新派生给调用方"，但"绑定调用方"在实现前容易被理解成只绑接收者。若把结果归属方记为提供者，提供者停用会连带撤销已经交付给调用方的结果，用户来不及保存 | 已在宿主核心中明确：结果句柄归属方为调用方。演示用例"已交付给调用方的结果不因下游提供者停用而失效"覆盖该行为 |
| R14 | P1 | 通知限流只写了"每来源每分钟最多 3 条"，未说明计数器是否按来源隔离。按全局计数会让一个来源的洪泛耗尽其他来源的紧急弹窗额度 | 已按来源独立计数；症状是合法来源被静默限流，属于契约未明确导致的实现分歧 |
| R15 | P1 | 原型清单把 `storage.plugin.read/write` 当权限名（R10 已记录），实现层的权限表若按字符串形状校验就会放行这类缩写 | 宿主改用固定权限目录校验，表外权限一律拒绝激活；演示用例覆盖 |

### 7.3 契约与实现的差距（尚未关闭）

- **方法级机器 schema 未补齐**：实现按契约文字编写，schema 文件仍只有服务级输入/输出示例；R05 的"方法级 schema 与样例"仍是 M1 冻结前的待办。
- **JSON Schema 校验为简化版**：实现只检查 `required` 与 `additionalProperties`，未覆盖 `type`、`pattern`、`enum` 与嵌套对象，也没有直接驱动 `plugin-manifest.schema.json`。Schema 文件与校验逻辑目前是两份并行的真相来源，属于 R12 类风险。
- **演示 manifest 尚未通过完整 schema**：三个演示插件的服务声明缺少必需 `description`，仍使用 `service/index.js` 演示约定，也未声明正式 `runtime.extension`。桌面 M1 打包前需迁移为 `extension/index.js` 并通过完整 manifest 校验。
- **插件运行时是演示替身**：独立子进程只验证 IPC、超时与回收；尚无插件信任、Restricted Mode、activation events、固定 Node.js runtime、Electron iframe 和正式 Extension SDK。
- **Agent API runtime 未实现**：当前 Agent 只是宿主内会话，验证可选 `agentCallable` 服务的授权语义；`agent-api` profile、模型循环、stdio SDK、事件流和结构化 run 结果均不存在。
- **未验证项保持未验证**：CSP/请求拦截、origin/顶层 frame/消息端口、Extension Development Host、移动信息收发、受限运行时和后台通知均无实测数据。

### 7.4 结论

M1 的核心接口语义（身份绑定、权限交集、资源句柄派生与撤销、绑定不抢占、统一 taskId、通知去重与降级）已经可用于后续实现，演示给出的 34 项断言全部通过。桌面选型已由 ADR 0009 关闭；R05 的机器 schema、正式 Extension Host/iframe 和 R06 的 Agent API runtime/SDK 仍是进入可用客户端阶段的阻塞项。

## 8. 桌面设计冻结补充：2026-09-18

根据第二轮设计审查，已冻结以下桌面约束：

- Electron 主进程作为 Desktop Runtime Supervisor；每个 profile 只有一个 Dart AOT Core Host，第二窗口和 Agent client 连接已有实例，Core Host 是工作区唯一写入宿主。
- Electron 与 Core Host 使用长度分帧的 stdio JSON-RPC；外部 client 通过 Linux 用户私有 UDS 或 Windows 当前用户 Named Pipe 连接 Supervisor。身份、背压、崩溃恢复和安全模式见 `contracts/desktop-core-ipc.md`。
- Extension Host 使用 Electron `utilityProcess` 和内置 Node，不附带第二套 Node；Dart Core 以 AOT 可执行文件交付。只有实测资源成本不可接受时才通过新 ADR 评估迁移。
- iframe 使用按工作区、安装和包摘要派生的 `ichat-plugin://<originKey>`；UI 只负责视图，服务只由 Extension Host 激活和执行。
- 桌面进程组总常驻内存超过 5 GiB 时提示用户审查。正在使用的插件不做 5 分钟定时回收；符合闲置条件连续 5 分钟后关闭，下次按激活事件重新创建。越过阈值不自动终止使用中的插件。
- 项目不运营默认插件源、签名、扫描或阻止列表。用户承担本地插件来源判断，宿主必须展示真实路径、摘要和 Node.js 代码执行风险。
- 开发顺序为 Linux、Windows、Android、iOS，不规划 macOS。桌面插件清单只允许 Linux、Windows，不包含 Android/iOS。
- Android 不追求运行时扩展性。服务器、去中心或仅本地连接模块由后续构建选择并随应用发布；账号、凭据、同步、冲突与后台到达属于入包模块，不成为通用移动宿主或桌面宿主的统一账号体系。桌面端对应责任由用户选择的插件承担。

以上为设计决定，仍需 M0/M1 测试证明。测试失败时按 ADR 0009 关闭第三方插件入口，不能静默放宽隔离或单写者要求。
